✅ IGEN, GARANTÁLT (backward irány)

3. Számla-Számla Láncolat (Invoice Chaining)

3.1 Hogyan Tároljuk a Láncolatot?

Nincs parent_id, nincs kapcsolótábla. A láncolat text-alapú matching:

MezőLeírásPélda
invoices.bizonylatsorszam A számla egyedi azonosítója E-THINK-2025-85
invoices.reference_number Hivatkozás egy másik számla bizonylatsorszámára E-THINK-2025-42

Ha egy számla reference_number = E-THINK-2025-42, az azt jelenti, hogy az E-THINK-2025-42 bizonylatsorszámú számla a szülő (hivatkozott bizonylat).

3.2 DB Oldali Láncolat – get_linked_invoices RPC

-- Rekurzív CTE, max 20 szint mélységig
WITH RECURSIVE chain AS (
  -- Seed: kiindulási számlák
  SELECT ... FROM invoices i
  WHERE lower(i.reference_number) = ANY(seed_bizonylat)
     OR lower(i.bizonylatsorszam) = ANY(seed_reference)
  UNION
  -- Rekurzió: mindkét irányban követi a linkeket
  SELECT ... FROM invoices i
  JOIN chain c ON (
    lower(i.reference_number) = lower(c.bizonylatsorszam)
    OR lower(i.bizonylatsorszam) = lower(c.reference_number)
  )
  WHERE depth < 20
)

3.3 Frontend Oldali Láncolat

A getLinkedInvoices() függvény (InvoicesPage.tsx:230-258) két irányban járja be a láncot:

  1. Felfelé (parents): Követi a reference_number → bizonylatsorszam láncot
  2. Lefelé (children): BFS kereséssel megtalálja az összes gyerek számlát

3.4 Kapcsolat Típusa

1:N (egy szülőnek több gyereke) de text-based, tehát:

  • Nincs referential integrity (FK)
  • Törlés esetén a lánc „csendben" megszakad
  • Elgépelés a reference_number-ben = elveszett kapcsolat
  • Nincs unique constraint a bizonylatsorszam-on → duplikátumok lehetségesek

3.5 Mi Történik Törléskor?

🔴 KRITIKUS – Lánc megszakadás védelem NINCS
  • A többi bizonylat NEM kap értesítést a törlésről
  • A reference_number hivatkozás árva (dangling) lesz
  • A frontend getLinkedInvoices() egyszerűen nem találja meg a törölt elemet → a lánc kettéválik
  • Nincs DB-szintű védelem (nincs FK, nincs trigger)

5. Kritikus Hibák és Problémák

🔴 KRITIKUS #1: salary.statusz manuális string

Fájl: hooks/useSalaryData.ts:120

// Kézi 'Kifizetve' string beírás a DB-be!
statusz: 'Kifizetve',

A salary tábla statusz mezője manuálisan van beállítva, NEM computed a transaction_id jelenlétéből. Ha utólag törlik a tranzakció-linket, a statusz nem áll vissza automatikusan.

🔴 KRITIKUS #2: Invoice Chaining – nincs törlés-védelem

A text-based matching (reference_number ↔ bizonylatsorszam) nincs DB szinten védve. Nincs FK, nincs trigger — a lánc csendben megszakadhat.

⚠️ FIGYELEM #3: transactions.matched_invoice_id – nincs FK

A transactions.matched_invoice_id mező nem rendelkezik FK constraint-tel. Ha egy számlát törölnek, a tranzakció matched_invoice_id mezője nem nullázódik automatikusan → árva hivatkozások.

ℹ️ MEGJEGYZÉS: invoices.statusz mező

Az invoices.statusz a feldolgozási állapotot jelzi (feldolgozás_alatt / feldolgozott), NEM a fizetési állapotot. A fizetési állapot a transaction_id jelenlétéből van compute-olva. A két koncepció nem keveredik, de a név félrevezető lehet.

ℹ️ Design Trade-off
A matched_invoice_id polimorf re­ferencia (3 táblára mutat­hat). Alternatív megoldás: szét­bontani 3 külön FK mezőre (matched_invoice_id, matched_nav_invoice_id, matched_salary_id).

6.3 Láncolat Stabilitásának Megőrzése

A) Soft-delete bevezetése:

Bizonylatok ne legyenek fizikailag törölhetők, csak statusz = 'torolt'. Így a lánc sosem szakad meg.

B) DB Trigger a lánc-megszakadásra:

CREATE OR REPLACE FUNCTION notify_chain_break() RETURNS trigger AS $$
BEGIN
  IF EXISTS (
    SELECT 1 FROM invoices 
    WHERE lower(reference_number) = lower(OLD.bizonylatsorszam)
  ) THEN
    RAISE WARNING 'Chain break: % is referenced', OLD.bizonylatsorszam;
  END IF;
  RETURN OLD;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER check_chain_break
  BEFORE DELETE ON invoices
  FOR EACH ROW EXECUTE FUNCTION notify_chain_break();

C) Frontend jelzés: Ha a reference_number nem feloldható, jelenjen meg egy ⚠️ ikon a „Kapcsolt bizonylatok" szekcióban „Megszakadt lánc" felirattal.
